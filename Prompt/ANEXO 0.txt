# ANEXO 0
# Matriz de Cumplimiento (Compliance Matrix)

> **Versión:** 1.0
>
> Este anexo constituye el mecanismo oficial para verificar que la implementación cumple completamente la especificación ejecutable.
>
> Ninguna funcionalidad podrá considerarse terminada hasta que todos los requisitos aplicables hayan sido implementados y validados.

---

# 0.1 Objetivo

La Matriz de Cumplimiento tiene los siguientes objetivos.

- Evitar requisitos olvidados.
- Facilitar revisiones de código.
- Facilitar auditorías técnicas.
- Facilitar migraciones entre versiones.
- Facilitar pruebas de regresión.
- Garantizar cumplimiento del protocolo.

---

# 0.2 Identificador de requisitos

Cada requisito deberá poseer un identificador único.

Formato:

REQ-XXX

Ejemplo.

REQ-001

REQ-002

REQ-003

Los identificadores nunca deberán reutilizarse.

---

# 0.3 Prioridad

Cada requisito deberá clasificarse utilizando uno de los siguientes niveles.

## Crítica

Su incumplimiento impide liberar el proyecto.

---

## Alta

Debe implementarse antes de la primera versión estable.

---

## Media

Puede implementarse en versiones menores.

---

## Baja

Corresponde a mejoras futuras.

---

# 0.4 Estado

Cada requisito deberá indicar su estado.

Valores permitidos.

NOT_STARTED

IN_PROGRESS

IMPLEMENTED

VALIDATED

REJECTED

DEPRECATED

---

# 0.5 Fuente

Cada requisito deberá indicar su fuente normativa.

Valores permitidos.

- Especificación Inertia.js

- Documentación Oficial Quarkus

- Esta especificación

Nunca utilizar otra fuente como referencia normativa.

---

# 0.6 Validación

Cada requisito deberá indicar cómo será validado.

Valores permitidos.

- Revisión de código

- Prueba unitaria

- Prueba de integración

- Benchmark

- Native Image

- Inspección manual

Un requisito podrá tener múltiples mecanismos de validación.

---

# 0.7 Responsable

Cada requisito deberá indicar el componente responsable de cumplirlo.

Ejemplo.

Inertia

ResponseProcessor

VersionProvider

HtmlRenderer

SharedDataRegistry

PartialReloadProcessor

RedirectProcessor

# 0.16 Regla de aceptación

Una fase únicamente podrá considerarse completada cuando.

- Todos los requisitos críticos estén en estado VALIDATED.

- No existan requisitos críticos en estado IN_PROGRESS.

- No existan requisitos críticos en estado NOT_STARTED.

---

# 0.17 Regla de liberación

La versión 1.0 únicamente podrá liberarse cuando.

✓ Todos los requisitos críticos estén validados.

✓ Todos los requisitos altos estén implementados.

✓ El proyecto compile correctamente.

✓ El proyecto funcione en JVM.

✓ El proyecto funcione en Native Image.

✓ El protocolo Inertia haya sido implementado completamente.

✓ No existan incumplimientos conocidos.

---

# 0.18 Regla de auditoría

Toda Pull Request deberá actualizar esta matriz.

Nunca se aceptará una Pull Request que implemente nuevos requisitos sin actualizar la Matriz de Cumplimiento.

Esta matriz constituye el registro oficial del estado de implementación del proyecto.
