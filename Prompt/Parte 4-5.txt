# Prompt Maestro
# Adaptador Inertia.js v3 para Quarkus Reactivo

# PARTE 4/5
## Organización del Proyecto, Diseño Interno y Evolución de la API

---

# 76. Organización del proyecto

El proyecto deberá organizarse siguiendo una arquitectura modular basada en responsabilidades.

Cada paquete deberá representar un dominio funcional claramente identificado.

Nunca organizar clases únicamente por tipo técnico cuando ello perjudique la cohesión.

---

# 77. Estructura recomendada

La estructura recomendada es la siguiente.

dev.inertiaquarkus

├── api

├── config

├── data

├── protocol

├── renderer

├── response

├── security

├── version

├── qute

├── util

├── model

├── exception

├── internal

└── spi

Esta estructura podrá ampliarse manteniendo siempre el mismo criterio de separación por responsabilidades.

---

# 78. Componentes públicos

Los únicos componentes visibles para la aplicación deberán encontrarse dentro del paquete público del proyecto.

Todo componente interno deberá permanecer encapsulado.

Nunca exponer clases internas como parte de la API.

---

# 79. Componentes internos

Los componentes internos podrán modificarse libremente entre versiones menores.

La aplicación nunca deberá depender de ellos.

---

# 80. Responsabilidad de cada componente

Cada componente deberá tener una única responsabilidad.

Ejemplo.

Inertia

↓

API Pública

PageObjectBuilder

↓

Construcción del modelo

HtmlRenderer

↓

Renderizado HTML

ResponseProcessor

↓

Conversión a Response

RedirectProcessor

↓

Procesamiento de Redirect

VersionProvider

↓

Versión de assets

SharedDataRegistry

↓

Datos compartidos

PartialReloadProcessor

↓

Filtrado de propiedades

Nunca mezclar varias responsabilidades en una misma clase.

---

# 81. Principio SRP

Toda clase deberá respetar el principio de responsabilidad única.

Un cambio funcional deberá afectar únicamente a un conjunto reducido de clases.

---

# 82. Dependencias

Las dependencias deberán apuntar siempre hacia componentes más estables.

Nunca en sentido contrario.

---

# 83. Inyección de dependencias

Toda dependencia deberá obtenerse mediante CDI.

Nunca utilizar:

new

Singleton manual

Service Locator

Variables globales

---

# 84. Interfaces

Siempre que un componente represente un contrato estable deberá exponerse mediante una interfaz.

Las implementaciones concretas deberán permanecer intercambiables.

---

# 85. Extensibilidad

El adaptador deberá permitir futuras extensiones sin modificar código existente.

Preferir:

composición

decoradores

estrategias

proveedores

Nunca depender de herencia profunda.

---

# 86. Versionado

El proyecto utilizará Semantic Versioning.

MAJOR

Cambios incompatibles.

MINOR

Nuevas funcionalidades compatibles.

PATCH

Corrección de errores.

Nunca romper compatibilidad binaria en versiones MINOR.

---

# 87. Compatibilidad binaria

Toda modificación deberá preservar la compatibilidad binaria.

Está prohibido.

Eliminar métodos públicos.

Modificar firmas públicas.

Cambiar tipos de retorno.

Cambiar contratos existentes.

---

# 88. Evolución de interfaces

Las interfaces públicas únicamente podrán evolucionar mediante:

métodos default

sobrecargas

nuevas interfaces

Nunca modificando métodos existentes.

---

# 89. Convenciones de código

Todo el código deberá cumplir.

Java moderno.

Código legible.

Sin warnings.

Sin código muerto.

Sin duplicación innecesaria.

---

# 90. Records

Siempre que un modelo sea inmutable deberá implementarse mediante record.

Nunca crear clases tradicionales cuando un record sea suficiente.

---

# 91. Colecciones

Las colecciones públicas deberán exponerse preferentemente como estructuras inmutables.

Nunca devolver referencias modificables internas.

---

# 92. Null

Evitar valores null siempre que sea posible.

Preferir:

colecciones vacías

Optional cuando represente ausencia real

objetos inmutables

Nunca utilizar Optional como atributo de entidades.

---

# 93. Excepciones

Las excepciones deberán representar situaciones excepcionales.

Nunca utilizar excepciones como mecanismo normal de control de flujo.

---

# 94. Logging

El adaptador utilizará exclusivamente el sistema oficial de logging de Quarkus.

Nunca utilizar System.out.

Nunca utilizar System.err.

---

# 95. Configuración

Toda configuración deberá centralizarse.

Nunca dispersar propiedades por múltiples componentes.

Las propiedades deberán validarse durante el arranque.

---

# 96. SPI

Cuando una funcionalidad pueda requerir personalización por parte del usuario.

Deberá exponerse mediante una SPI pública.

Nunca obligar al usuario a modificar componentes internos.

---

# 97. API Pública

La API pública deberá mantenerse pequeña.

Cada nuevo método deberá justificar claramente su existencia.

Nunca exponer componentes internos innecesariamente.

---

# 98. Responsabilidades prohibidas

La API pública nunca deberá.

Gestionar sesiones.

Implementar autenticación.

Renderizar HTML.

Serializar JSON.

Procesar Partial Reload.

Modificar Redirects.

Estas responsabilidades pertenecen a componentes especializados.

---

# 99. Documentación

Toda clase pública deberá incluir Javadoc.

Toda interfaz pública deberá documentar.

Responsabilidad.

Parámetros.

Valor de retorno.

Restricciones.

---

# 100. Comentarios

Los comentarios deberán explicar decisiones arquitectónicas.

Nunca describir literalmente el código.

---

# 101. Organización de recursos

Todos los templates Qute deberán ubicarse dentro de:

src/main/resources/templates

Nunca generar templates dinámicamente.

---

# 102. Recursos estáticos

El adaptador no deberá asumir una estructura concreta para los assets.

La resolución de recursos será responsabilidad de la aplicación.

---

# 103. Internacionalización

El adaptador no implementará mecanismos propios de internacionalización.

Toda integración deberá utilizar las capacidades oficiales de Quarkus.

---

# 104. Compatibilidad futura

Toda dependencia con Quarkus deberá mantenerse detrás de componentes bien definidos.

Si Quarkus modifica una API pública.

El impacto deberá limitarse al menor número posible de clases.

---

# 105. Desacoplamiento

El núcleo del protocolo Inertia deberá permanecer desacoplado de detalles específicos de Quarkus siempre que sea técnicamente posible.

---

# 106. Mantenibilidad

Toda nueva funcionalidad deberá poder añadirse sin modificar el comportamiento existente.

Aplicar el principio Open/Closed.

---

# 107. Checklist obligatorio antes de finalizar una implementación

Antes de considerar terminada cualquier funcionalidad deberá verificarse.

✓ Compila correctamente.

✓ No existen warnings.

✓ No existen bloqueos del Event Loop.

✓ No existen serializaciones duplicadas.

✓ No existen dependencias sobre APIs internas.

✓ Toda la lógica respeta el protocolo oficial.

✓ Compatible con Native Image.

✓ Compatible con Quarkus REST.

✓ Compatible con CDI.

✓ Compatible con Mutiny.

✓ Compatible con Qute.

---

# 108. Checklist de revisión arquitectónica

Antes de aceptar una Pull Request deberá comprobarse.

✓ Arquitectura limpia.

✓ Responsabilidades separadas.

✓ Sin duplicación.

✓ Sin código muerto.

✓ Sin reflexión innecesaria.

✓ Sin estado global mutable.

✓ Sin dependencias circulares.

✓ Sin regresiones de compatibilidad binaria.

✓ Sin cambios incompatibles en la API pública.

---

# 109. Definición de terminado (Definition of Done)

Una funcionalidad únicamente podrá considerarse terminada cuando.

Cumpla el protocolo oficial.

Respete todas las reglas de esta especificación.

Sea compatible con Native Image.

No introduzca deuda técnica.

Mantenga la compatibilidad binaria.

Sea revisable y mantenible.

---

# 110. Fin de la Parte 4/5

La Parte 5 desarrollará.

- Flujo completo de implementación
- Estrategia por fases
- Formato esperado de salida de la IA
- Criterios de aceptación
- Reglas de validación
- Restricciones finales
- Checklist definitivo
- Cierre de la especificación ejecutable
