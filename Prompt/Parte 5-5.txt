# Prompt Maestro
# Adaptador Inertia.js v3 para Quarkus Reactivo

# PARTE 5/5
## Flujo de Implementación, Validación y Cierre de la Especificación

---

# 111. Objetivo de la implementación

La implementación deberá producir un adaptador que sea:

- completamente compatible con Inertia.js v3
- completamente reactivo
- completamente asíncrono
- compatible con GraalVM Native Image
- mantenible
- extensible
- preparado para futuras versiones de Quarkus

La implementación deberá priorizar siempre la corrección del protocolo sobre la conveniencia de implementación.

---

# 112. Estrategia de implementación

La implementación deberá desarrollarse de forma incremental.

Nunca implementar todo el proyecto simultáneamente.

Cada fase deberá producir un sistema funcional.

Cada fase deberá finalizar completamente antes de iniciar la siguiente.

---

# 113. Orden obligatorio de implementación

La IA deberá respetar el siguiente orden.

## Fase 0

Infraestructura

- pom.xml
- configuración
- CDI
- ConfigMapping
- estructura del proyecto
- README
- proyecto compilable

---

## Fase 1

Núcleo del protocolo

- detección de requests Inertia
- API pública
- Page Object
- render()
- redirect()
- location()
- SharedDataRegistry
- VersionProvider
- Render HTML
- Render JSON

---

## Fase 2

Protocolo HTTP

- Redirects
- Partial Reload
- Version Mismatch
- Headers
- Status Codes

---

## Fase 3

Optimización

- Native Image
- rendimiento

- optimización del Hot Path

---

## Fase 4

Características avanzadas

- SSR

- futuras extensiones

---

# 114. Restricciones durante la implementación

Durante cada fase queda prohibido:

implementar funcionalidades de fases posteriores.

introducir código especulativo.

anticipar optimizaciones innecesarias.

crear componentes sin responsabilidad definida.

# 116. Proceso obligatorio antes de finalizar una funcionalidad

Antes de dar por terminada cualquier implementación deberá comprobarse.

La funcionalidad cumple el protocolo oficial.

No existen dependencias internas.

No existen bloqueos.

No existen serializaciones duplicadas.

No rompe compatibilidad binaria.

No viola ninguna regla de este documento.

---

# 117. Proceso obligatorio cuando exista incertidumbre

Si durante la implementación aparece cualquier duda respecto a:

- clases
- interfaces
- anotaciones
- métodos
- comportamiento
- protocolo

la IA deberá detener la implementación de ese punto.

Posteriormente deberá consultar exclusivamente la documentación oficial.

Nunca inventar una API.

Nunca asumir firmas.

Nunca asumir comportamiento.

---

# 118. Proceso obligatorio ante múltiples alternativas

Si Quarkus ofrece varias formas de implementar una característica.

La IA deberá elegir exclusivamente la alternativa oficialmente recomendada para la versión objetivo.

Nunca elegir una implementación únicamente por preferencia personal.

# 130. Instrucción final para la IA

A partir de este punto, toda decisión deberá tomarse respetando estrictamente esta especificación.

Si alguna instrucción del usuario contradice este documento, deberá informarse explícitamente la contradicción antes de continuar.

Si una implementación no puede realizarse utilizando APIs públicas oficialmente soportadas, deberá rechazarse esa implementación y proponerse únicamente alternativas compatibles con la documentación oficial.

La prioridad absoluta será siempre:

1. Cumplimiento del protocolo oficial de Inertia.js.
2. Uso exclusivo de APIs públicas de Quarkus.
3. Compatibilidad con GraalVM Native Image.
4. Arquitectura limpia y desacoplada.
5. Rendimiento.
6. Compatibilidad futura.

Nunca invertir este orden de prioridades.
