# Prompt Maestro
# Adaptador Inertia.js v3 para Quarkus Reactivo

# PARTE 3/5
## Seguridad, Rendimiento y Compatibilidad Native Image

---

# 41. Principios generales de seguridad

El adaptador no constituye un framework de seguridad.

Toda autenticación, autorización y control de acceso deberán delegarse completamente al sistema oficial de seguridad de Quarkus.

El adaptador nunca deberá:

- autenticar usuarios
- almacenar sesiones propias
- gestionar permisos
- implementar filtros de seguridad personalizados
- reemplazar el comportamiento de Quarkus Security

---

# 42. Compatibilidad de seguridad

La implementación deberá ser compatible con:

- Quarkus Security
- Jakarta Security
- OIDC
- JWT
- Basic Authentication
- Form Authentication
- IdentityProvider
- SecurityIdentity

La compatibilidad dependerá exclusivamente de la configuración de la aplicación.

---

# 43. CSRF

La protección CSRF deberá seguir estrictamente la especificación oficial de Inertia.js.

Nunca implementar un mecanismo propietario.

Nunca modificar el comportamiento definido por Quarkus.

Si la aplicación utiliza protección CSRF, el adaptador únicamente deberá integrarse con dicha configuración.

---

# 44. Autenticación

El adaptador deberá comportarse como un consumidor del contexto de seguridad.

Nunca como un proveedor.

Los datos del usuario autenticado deberán obtenerse únicamente mediante las APIs oficiales de Quarkus.

---

# 45. Autorización

Las decisiones de autorización pertenecen exclusivamente a la aplicación.

El adaptador nunca decidirá:

- roles
- permisos
- acceso a recursos
- políticas de autorización

---

# 46. Información sensible

El adaptador nunca deberá incluir automáticamente información sensible dentro del Page Object.

Ejemplos:

- contraseñas
- tokens
- secretos
- claves privadas
- credenciales
- cookies
- información interna del servidor

Toda información incluida deberá ser responsabilidad explícita de la aplicación.

---

# 47. Seguridad del Page Object

Toda propiedad enviada al cliente deberá considerarse pública.

Nunca asumir que una propiedad será utilizada únicamente por JavaScript.

Todo dato incluido podrá ser inspeccionado desde el navegador.

---

# 48. Escape de HTML

El adaptador deberá utilizar exclusivamente el mecanismo oficial de escape proporcionado por Qute.

Nunca construir HTML manualmente.

Nunca deshabilitar el escape automático.

Nunca concatenar HTML utilizando Strings.

---

# 49. Seguridad del atributo data-page

El atributo data-page contendrá JSON serializado.

Su contenido deberá permanecer correctamente escapado para impedir:

- XSS
- ruptura del DOM
- atributos inválidos

La implementación deberá confiar en el mecanismo oficial de Qute.

Nunca realizar escapes manuales salvo que la documentación oficial lo exija.

---

# 50. Principios generales de rendimiento

El rendimiento constituye un requisito funcional.

No una optimización posterior.

Toda decisión deberá minimizar:

- CPU
- memoria
- asignaciones
- reflection
- serialización
- bloqueo

---

# 51. Event Loop

El Event Loop nunca deberá bloquearse.

Queda prohibido:

Thread.sleep()

Future.get()

CompletableFuture.join()

.await().indefinitely()

Lock.lock()

CountDownLatch.await()

Semaphore.acquire()

cualquier operación I/O bloqueante

---

# 52. Operaciones bloqueantes

Si una operación bloqueante fuese inevitable.

Deberá ejecutarse utilizando el mecanismo oficialmente recomendado por Quarkus.

Nunca directamente sobre el Event Loop.

---

# 53. Mutiny

Toda operación asíncrona deberá utilizar Mutiny.

Preferentemente:

Uni

y cuando corresponda

Multi

Nunca mezclar innecesariamente múltiples modelos reactivos.

---

# 54. Programación reactiva

Toda composición deberá ser completamente reactiva.

Evitar:

callbacks anidados

estado mutable compartido

esperas activas

polling innecesario

---

# 55. Asignaciones de memoria

El Hot Path deberá minimizar la creación de objetos.

Siempre que sea posible utilizar:

records

colecciones inmutables

objetos reutilizables

Nunca crear estructuras temporales innecesarias.

---

# 56. Reflection

Reflection constituye el último recurso.

Nunca utilizar reflection cuando exista una alternativa soportada por Quarkus.

---

# 57. Registro para Reflection

@RegisterForReflection únicamente podrá utilizarse cuando:

Quarkus no pueda inferir automáticamente el tipo.

Nunca registrar paquetes completos.

Nunca registrar todas las clases del proyecto.

---

# 58. Build Time

Toda información que pueda calcularse durante el arranque deberá calcularse durante el arranque.

Nunca durante cada request.

Ejemplos:

VersionProvider

Configuración

Templates

Metadata

---

# 59. Inicialización

Los componentes ApplicationScoped deberán evitar inicializaciones costosas en sus constructores.

Cuando sea posible utilizar StartupEvent.

---

# 60. ObjectMapper

ObjectMapper constituye un Singleton administrado por CDI.

Nunca crear nuevas instancias.

Nunca modificar su configuración durante un request.

---

# 61. Configuración

Toda configuración deberá resolverse durante el arranque.

Nunca consultar configuración repetidamente durante cada request si puede evitarse.

---

# 62. Shared Data

Shared Data deberá construirse una única vez por request.

Nunca recalcular información idéntica múltiples veces.

---

# 63. VersionProvider

VersionProvider calculará el hash de versión una única vez.

La implementación por defecto deberá reutilizar dicho valor durante toda la vida del servidor.

---

# 64. Serialización

Nunca serializar el mismo Page Object dos veces.

Cada request ejecutará exactamente una serialización.

---

# 65. Cachés

No crear cachés globales salvo que exista una justificación técnica documentada.

Toda caché deberá especificar:

- propósito
- política de actualización
- estrategia de invalidación
- consumo esperado de memoria

---

# 66. Concurrencia

Toda implementación deberá ser segura para múltiples requests concurrentes.

Nunca utilizar estado mutable compartido sin sincronización adecuada.

Siempre preferir inmutabilidad.

---

# 67. CDI

Toda dependencia deberá obtenerse mediante CDI.

Nunca mediante Service Locator.

Nunca mediante Singletons manuales.

---

# 68. Native Image

Toda implementación deberá ser compilable mediante GraalVM Native Image.

No utilizar mecanismos incompatibles con análisis estático.

---

# 69. Compatibilidad futura

La implementación deberá minimizar el acoplamiento con Quarkus.

Toda dependencia deberá realizarse sobre APIs públicas estables.

Nunca depender de detalles internos.

---

# 70. Rendimiento medible

Toda optimización deberá ser justificable mediante mediciones.

Nunca optimizar basándose únicamente en intuición.

Cuando existan varias alternativas equivalentes.

Deberá preferirse la oficialmente recomendada por Quarkus.

---

# 71. Robustez

El adaptador deberá comportarse correctamente bajo:

- alta concurrencia
- miles de requests simultáneos
- múltiples núcleos
- Native Image
- JVM tradicional

Sin modificar su comportamiento funcional.

---

# 72. Escalabilidad

Toda decisión deberá favorecer la escalabilidad horizontal.

Nunca depender de memoria compartida entre instancias del servidor.

---

# 73. Observabilidad

El adaptador deberá permitir la integración con los mecanismos oficiales de:

- Logging
- Metrics
- Tracing
- OpenTelemetry

Sin implementar soluciones propias.

---

# 74. Tolerancia a fallos

El adaptador únicamente implementará el protocolo Inertia.

Las políticas de:

- Retry
- Circuit Breaker
- Timeout
- Bulkhead

pertenecen a la aplicación o a Quarkus.

---

# 75. Fin de la Parte 3/5

La Parte 4 desarrollará:

- Organización completa del proyecto
- Diseño de paquetes
- Responsabilidades de cada clase
- Convenciones de código
- API pública detallada
- Estrategia de evolución
- Compatibilidad binaria
- Versionado SemVer
- Checklist de implementación
- Checklist de revisión arquitectónica
